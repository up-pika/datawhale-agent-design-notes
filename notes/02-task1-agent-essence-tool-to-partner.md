# Task 1 · Agent 的本质：从工具到伙伴

> **材料**：DataWhale 共学 · 黄佳《Agent 设计模式》**第 3 章**（从设计到演化，欢迎来到 Agent 时代）中 **3.1 及前后衔接段落**（含 3.2 开篇对「心智架构」的定位）。  
> **说明**：以下为讲义要点摘录与结构化整理，不新增讲义未出现的论断；若有个人衔接用语，见文末「补充标注」。

---

## 0. 章节定位（闭环入口）

当 **LLM 处于架构核心** 时，软件不再只是响应指令，而开始具备 **意图** 与 **能动性（agency）**。

讲义归纳软件性质的三重转变：

| 维度 | 从 → 到 |
|------|---------|
| 角色 | 工具 → **主动观察者**（感知环境） |
| 形态 | 无状态函数 → **有记忆、有身份的主体** |
| 关系 | 孤立计算节点 → **可协作的社会成员** |

概括：**从「设计」一套系统，走向「培育」一种物种**（与图 3-1「Agent 是新物种」呼应）。

---

## 1. 何谓 Agent（3.1 总起）

- **技术视角**：可理解为持续运行、**反复调用 LLM API** 的循环结构（讲义用语：**死循环脚本**）。
- **交互哲学视角**：人机关系从 **「命令与控制」** 转向 **「意图与协作」**。

---

## 2. 从命令到对话（3.1.1）

**交互原语升级**：伙伴式协作体现为——**澄清**（问数据规模、历史等）→ **给建议**（如混合推荐策略）→ **讲清原因与路径**（如冷启动、分步路线图）→ **主动提出代劳**（如写初版框架）→ **多轮延续**（如时间衰减等后续问题）。

**身份对比（讲义）**

| | 工具 | Agent |
|---|------|--------|
| 性质 | 被动、机械 | 主动、智能 |
| 能力边界 | 固定输入输出；无状态、难理解情境 | 感知环境、自主思考规划、行动；可从经验中持续学习 |
| 行为 | 等命令 → 执行 → 再等 | （同上「主动」链） |

**人机交互单元演进**

- **CLI**：单元 ≈ **命令**  
- **GUI**：单元 ≈ **点击**  
- **共同前提（CLI/GUI）**：人扛 **How（步骤）**，机器只执行。  
- **Agent 时代**：单元 ≈ **对话 / 意图**；**How 交给 Agent**（例：「把文档改正式一点」由 Agent 读内容、改写法、保存）。

**结果**：复杂度从用户脑中大量「菜单、步骤、命令记忆」，部分转移到系统在后台完成的操作细节；关系从 **「你执行」** 到 **「一起把事情做成」**。

---

## 3. 意图理解（3.1.2）

对话不仅是自然语言，还涉及 **意图理解**、**上下文延续（上下文工程）**、**任务拆解**。

- **传统软件**：偏字面、缺主动；难以理解「隐含意思」。  
- **Agent 核心能力之一**：做 **「模糊 → 精确」的翻译**——把口语意图经推理、消歧、补参，变成可执行的精确调用（讲义称 **「意图编译器」**，实时把人的意图编译成机器可执行动作）。

**意图理解的四个层次（技术视角）**

1. **语义理解**：从表述中提取动作、对象、范围、约束（可用结构化 intent 模型）。  
2. **目的识别**：不止「说了什么」，还要 **想达成什么**（业界强调从显式指令推断隐式目标；讲义举 **OpenAI o1 的 Reasoning Tokens** 作为通过推理捕获隐意图的机制之一）。  
3. **上下文关联**：把意图落到具体环境（代码结构、目录、偏好、安全约束、历史任务等）。讲义强调：**Agent 须基于当前世界状态做判断与决策**。  
4. **风险评估与澄清**：意图不清时 **先问再动**，减少误操作、服务安全与准确。

**结构化意图与可靠性（讲义代码思想）**：意图可作为结构化对象（如 `action` / `target` / `constraints` / `confidence`）；**置信度低时不盲执行**，转而澄清——这是 Agent **可靠性**的重要表现。

---

## 4. 记忆与身份（3.1.3）

- **工具**：用完即走，像每次打开的「白板」，**不延续**过往交互。  
- **伙伴型 Agent**：有 **记忆**，跨会话维持连续性，逐渐更懂用户（图 3-3：Agent 像伙伴一样「再次见到你」）。

**记忆的实质（讲义）**：基座 LLM **本身无状态**；记忆是依靠 **上下文工程** 营造的 **连续性幻觉**。

- **短期（会话）记忆**：本会话输入、话题、代码片段、纠错等；用于多轮一致、少重复追问、基于上下文的连续推理；大规模上下文中常配合 **摘要、过滤、结构化**。  
- **长期记忆**：跨会话偏好、常用栈、历史项目与问题类型、人设等；技术路径提及 **向量库** 及 **Mem0、GraphRAG、混合记忆** 等，使记忆可建模、可检索。

**身份（Identity）**  
由 **System Prompt** 等承载：把通用模型 **收敛为稳定人设与行为准则**（价值取舍、专业边界、安全优先等）。

讲义给出的对照：

- **记忆** = **连续性**（知道用户是谁、之前说过什么）  
- **身份** = **稳定性**（Agent 自身是谁、如何一贯地行动与表达）  

二者在工具时代几乎不存在，却是软件进化为 **协作者** 的基础。

---

## 5. 上下文工程（3.1.4）

- **核心判断**：对 Agent 而言，**上下文就是它的整个世界**（图 3-4：物理世界 → 上下文选择器 → 模型窗口/Prompt）。  
- **模型不主动感知世界**，只靠输入文本推理；失败常源于 **上下文错、缺、乱**，而非单纯「模型不够强」（Garbage In, Garbage Out）。

**与 Prompt 工程的分工（讲义）**

- Prompt 工程：偏 **「怎么说」**。  
- 上下文工程：偏 **「给 Agent 看什么」**——把最关键信息以合适结构塞进窗口；本质是 **为 Agent 造「数字感官」**（把世界状态序列化为文本）。

**劣质上下文的典型风险**：信息不全导致跑偏；信息过多难以抓重点；结构混乱导致模型「迷路」。窗口变大（如几十万到百万 token）后，**筛选与组织**更重要。

**三类上下文（讲义）**

1. **用户上下文**：风格、历史偏好、技术栈、当前在做什么任务等。  
2. **环境上下文**：目录与代码、分支、日志与栈、变量值、API 返回、运行时状态等。  
3. **任务上下文**：多步任务中已完成子任务、进度、依赖是否就绪、历史工具调用等（与 LangGraph 类工作流相关）。

**从「堆字」到「结构」**：高质量上下文重在 **筛选与压缩**——选择性上下文、结构化摘要、图结构检索、优先级/「思考模式」下的权重等；比喻：**手电光照哪里，决定能不能解题**。

## 6. 任务分解（3.1.5）

**定义**：把高层 **目标** 变成可执行的 **步骤**；讲义视为 Agent **智力水平**的重要指标。

**两个环节**：**规划**（拆子目标）→ **映射**（子目标落到具体动作或可调用工具）。

**范式对比**

- **工具时代**：复杂度的拆解主要在 **人**（例：修 bug = 找人改文件 → 跑测，由人逐步指定）。  
- **Agent 时代**：拆解与执行的认知负荷 **向系统转移**；可支撑远超单次 API 调用的长程任务。

**规划层（Planner）三职能（讲义）**：**理解**（把含糊目标变成明确需求）→ **计划**（可执行多步方案）→ **执行与批判**（根据新观测调整计划，如瓶颈从 I/O 换到 CPU）。

**任务分解三步法**

1. **理解目标**（含真实需求，非字面）  
2. **确定路径**（简洁、可执行、可中断检查、能随反馈调整）  
3. **管理执行**（工具调用、失败重试、异常处理、结果校验、进度汇报；LangGraph / AutoGen / CrewAI 等侧重把「聊天模型」变成「可靠执行器」）

**自我审查趋势**：先出计划 → **批判可行性** → 再执行（讲义举 DeepSeek、Qwen3「思考模式」等研究方向）。

**与上下文工程的关系**：上下文工程帮 Agent **「看清楚」**；任务分解帮 Agent **「做对」**——两者扣成完整执行链。

## 7. 工具、技能与行动策略（3.1.6）

**没有工具则 LLM 如「缸中之脑」**：能想、能写 SQL/行程，却 **不能连库、不能订票**。讲义比喻：**LLM = 脑**，API/函数等 = **肌肉**；本节侧重控制这些肌肉的 **策略层**。

**「做」vs「说」**：Agent 与纯聊天机器人的分界在于 **行动**。需要：**工具选择**（在目标与上下文下选对工具）与 **策略制定**（安全、可靠、可预期的路径与纠错）。

**工具对 Agent 的三要素（超越函数签名）**

1. **功能描述**（语义说明书）  
2. **参数约束**（如 JSON 契约）  
3. **副作用声明**（只读/写数据/触发外系统等安全提示）

**标准化**：**MCP（2024）** 等推动工具描述可插拔；与 LangChain Tools、OpenAI/Anthropic Function Calling 等并列为现代 Agent 基础设施。

**从「工具」到「技能（Skill）」**（讲义定义）

- **工具**：原子操作（执行 SQL、HTTP、读写文件等）。  
- **技能**：面向业务的封装（月报、Code Review、退款流程等）。  
- **公式**：**Skill = Tool + 领域知识 + SOP（标准作业程序）**  

动机：裸 API「冷」且危险（如直接 `delete_user`）；封装成带业务规则与安检的 **技能**，Agent 才掌握 **「正确地做」**，而不仅是 **「会做」**——知识资产化、**数字员工**、继承企业「DNA」。

**工具/技能选择（高级形态）**：先判断要不要用、何时用、用哪个、上下文够不够、副作用、是否先校验；再抽取参数、生成结构化输入、执行；可 **多工具编排**（搜文档 → 跑样例 → 数学工具验证）。LangGraph、AutoGen、MCP 等强调此链路。

**ReAct 核心循环（DeepMind，讲义）**：**Thought → Action → Observation**，根据观察修正下一步；**行动增强的推理**，在环境中试错、逼近解。

**行动策略：安全与边界（讲义）**

- **三道防线**：**只读沙箱**（调研阶段非破坏）→ **人在回路（HITL）**（高风险写操作前人工审）→ **确定性护栏**（执行层硬规则，如禁止删根目录）。  
- **行为规范三层次**：**安全**（越界则拒）→ **可解释**（展示计划与选工具理由）→ **可控**（关键步骤可介入）。

**人机角色**：从 **操作员**（逐步亲手点）→ **监督者与评估者**（定目标、审计划、授权关键动作、评价结果）。**Copilot**：人主导、AI 辅助；**Autopilot**：AI 执行、人监督（图 3-6）；本体层面 Agent 是 **感知—记忆—推理—行动** 融合的数字存在，既是 **镜子**（理解/延伸意图）也是 **伙伴**（协作与担责）。

## 8. 闭环：心智架构与和传统软件的对比（3.2 开篇）

- **智能** 被表述为在与环境 **持续交互的循环** 中展开的动态过程。  
- **传统软件（如 MVC/微服务）**：多为 **输入 → 处理 →输出** 的线性管道，一次结束。  
- **Agent 架构**：必须引入 **循环**；Agent 像 **进程**（如讲义中的 `while(alive)` 意象），而非单次 **函数**。

**图 3-7（心智架构）要点**：**感知**（上下文映射）→ **推理**（拆解与思维链）→ **行动**（工具调用）；行动结果经 **反馈** 回到推理，**状态/结果** 回到感知；对外经 **调用/副作用** 作用于 **环境/工具**，再经感知回收——形成 **感知—推理—行动** 的闭环。

---

## 9. 一句话收束（讲义逻辑串）

软件因 LLM 从 **被动工具** 走向 **能协作的主体**：交互上 **命令/点击 → 意图与对话**；能力上 **意图编译（四层）+ 记忆与身份 + 上下文工程 + 任务分解**；落地上 **工具/技能化行动 + ReAct + 安全与人在回路**；架构上 **循环而非一次性管道**——**从「你执行」到「一起把事情做成」**，同时人上升为 **监督与评估**。
